# Internationalization (i18n) — Spec

Audience: maintainers and Claude Code sessions wrapping new UI strings or adding
a language catalog. This is the shipped contract for the foundation that landed
in Pass 43.1 (machinery + a single-page pilot). The pre-implementation design
rationale lives in `docs/superpowers/specs/2026-06-10-i18n-foundation-design.md`;
this doc is the durable how-to.

Vocabulary: a locale's `.po` (human-editable) + `.mo` (compiled) pair is a
**catalog**. "Language pack" is the roadmap's user-facing synonym, not a second
concept.

---

## 1. Approach

Flask-Babel with **source-text message IDs** (the gettext standard). The English
source text *is* the catalog key, so wrapping a string is zero-friction — no
separate key registry. `pybabel extract` walks templates + Python into
`messages.pot`; per-locale catalogs live under `translations/<code>/LC_MESSAGES/`.

Scope shipped in 43.1: the machinery, a per-user language setting, a pseudolocale
QA catalog, and a pilot migration of `templates/login.html` + the logout flash.

Scope completed in 43.2 / 43.3 / 43.5 (this bundle):

- **43.5** — bulk migration of the remaining ~60 templates + the route flash /
  `error()` sites, plus six real human-language catalogs (`de`, `fr`, `es`,
  `it`, `ja`, `pt_BR`). Same wrap contract as §2.
- **43.3** — client-side strings (toasts, modal copy built in JS). A `t()`
  helper reads a server-emitted `window.I18N` map. See §6.
- **43.2** — display translation of the DB-stored canonical multi-value labels
  (genre / perspective / dimension / modes / game_structure). The DB keeps
  canonical English; only the *rendered label* is translated. See §7.

Scope added in 43.6:

- **43.6** — exhaustive wrapping of the remaining `error()` / JSON-error sites
  across `routes/*.py` + `services/*.py` and the Wishlist page (same catalog
  contract as §2), **plus** long-form content (the help manual and recent
  changelog) translated as **whole per-locale files** rather than through the
  catalog. See §9.

The 43.1/43.2/43.3/43.5/43.6 catalog work shares **one** gettext catalog and the
source-text-msgid convention — there is no second translation store. The one
deliberate exception is 43.6's long-form content (§9), which is too large and
markup-heavy to route through gettext.

## 2. Wrap-new-strings contract

- **Templates:** wrap visible text in `{{ _('...') }}`. Wrap user-visible
  attribute strings too — `title=`, `aria-label=`, `placeholder=`. Do **not**
  wrap template comments, CSS class names, or brand tokens (keep "RetroDB" out
  of the msgid: `{{ _('Login') }} - RetroDB`).
- **Python:** wrap flash + error copy — `flash(_('You have been logged out'))`,
  `error(_('...'))`. The msgid must match the source literal byte-for-byte.
  Interpolate with the **gettext-named** form on the translated string —
  `_('Scraped %(n)s games') % {'n': n}`, never `_('Scraped %s games' % n)` (the
  latter bakes the value into the msgid). `%(name)s` is placeholder-guarded by the
  pseudolocale (§5), the Python analogue of §6's JS `{n}` brace form.
- **JS strings** (toasts, modal copy built client-side) are wrapped with the
  `t('...')` helper, **not** `_()` — see §6. (The login pilot deliberately
  leaves its inline `<script>` strings English; it predates §6 and is not worth
  re-touching.)
- **Dynamic data** (usernames, free-text fields) is not wrapped. The DB-stored
  canonical multi-value labels (genre / perspective / dimension / modes /
  game_structure) are a special case: the stored value stays canonical English,
  but the *rendered label* is translated through the §7 layer — never wrap them
  with a literal `_()` at the storage or query layer.

Every string added to a wrapped page must be re-extracted (§4) or it ships
untranslated.

## 3. Locale-selection chain

`app.py::select_locale()` (registered via `Babel(app, locale_selector=...)`)
resolves the active locale per request, in order:

1. **User preference** — `g.user_settings.get('locale_preference')`, behind an
   outer `if g.get('user_settings'):` guard. `g.user_settings` is the per-user
   settings dict; the preference itself lives in the `locale_preference` column
   (`TEXT DEFAULT 'en'`), saved via `/api/users/settings`. Both guards matter: the
   outer one skips the branch when no user is loaded (`g.user_settings` is
   `None`); the inner `.get()` (not a subscript) returns `None` rather than
   `KeyError` for a row written before the column existed (or any settings dict
   missing the key).
2. **Session** — `session['locale']` (retained for a future anonymous switcher;
   no UI writes it in v1).
3. **`Accept-Language`** — the browser's best match.
4. **`'en'`** — default.

Every branch is guarded by membership in `services.i18n.available_locales()`, so
a stale or removed locale never raises — it degrades to `'en'`.

`available_locales()` enumerates `translations/*/LC_MESSAGES/messages.mo` plus
the implicit `'en'`, and is the single source of truth shared by the selector,
the `/api/users/settings` locale validator, and the Settings dropdown.

## 4. Catalog regeneration workflow

Run from the repo root, **after** wrapping new strings (extract must see the new
msgids or they never reach the catalogs and the completeness test fails):

```bash
python3 build_js.py                                  # 0. regenerate services/js_i18n_strings.py (JS msgid manifest + _() bridge anchors, §6)
pybabel extract -F babel.cfg \
    --ignore-dirs='.* __pycache__ node_modules venv .venv env build dist staging tests' \
    -o messages.pot .                                # 1. snapshot all msgids — templates + Python (incl. the JS bridge module) + canonical labels
pybabel update  -i messages.pot -d translations      # 2. MERGE new msgids into the real .po catalogs (keeps existing translations)
python3 scripts/gen_pseudolocale.py                  # 3. regen the pseudolocale .po wholesale from messages.pot
pybabel compile -d translations                      # 4. compile every .po -> .mo
```

Several non-obvious points:

- **JS msgids ride the `[python:]` mapping, not a `[javascript:]` one.** There is
  deliberately no JS extractor (Babel's mis-parses this codebase — see §6). Step 0
  regenerates `services/js_i18n_strings.py`, whose generated `_('...')` anchors the
  default `_` keyword extracts. The canonical-label module (§7) extracts the same
  way. So the default keywords suffice — no `-k` flag is needed.
- **`--ignore-dirs` is mandatory, not cosmetic.** Babel's default directory
  filter skips every directory whose name starts with `.` **or `_`** — which
  silently drops all of `templates/_modals/`, `templates/_settings_tabs/`, and
  `templates/_macros/` (the entire settings UI + edit modal). The flag *replaces*
  that filter, so the list must re-enumerate the junk dirs to skip (dotdirs,
  `__pycache__`, virtualenvs, `build`/`dist`/`staging`, and `tests` — test files
  must not seed msgids). Keep the list byte-identical across this command,
  `babel.cfg`'s comment, and `scripts/check_i18n_fresh.py::I18N_IGNORE_DIRS`, or
  the §6 freshness gate diffs a differently-scoped `messages.pot` and red-lights.
- **Step 2 (`update`) vs step 3 (`gen_pseudolocale`)** differ deliberately. Real
  human catalogs must be *merged* (`pybabel update`) so a re-extract never wipes
  existing translations — new msgids land empty (untranslated), obsolete ones are
  commented out. The pseudolocale is *regenerated wholesale* (every msgstr is a
  pure function of its msgid), so step 3 overwrites whatever step 2 wrote to `eo`.
  Order matters: update (all locales) → regen pseudo (`eo` only) → compile (all).
- **Extract precedes pseudo.** `gen_pseudolocale.py` reads `messages.pot`
  (and `sys.exit`s if it is absent), so step 3 must follow a successful step 1 —
  otherwise it pseudo-localizes a stale snapshot silently.
- **Step 0 precedes step 1.** `pybabel extract` (step 1) reads the `_()` anchors
  that `build_js.py` (step 0) regenerates into `services/js_i18n_strings.py`, so a
  stale or un-run step 0 means JS msgids miss the catalog. Both must also be
  committed together, or the §6 gate's clause (c) (`JS_I18N_KEYS ⊆ messages.pot`)
  reds.
- **Birthing a new locale.** Step 2's `pybabel update` only refreshes catalogs
  that already exist on disk; it does **not** create one. Each brand-new locale
  (the 43.5 set is `de fr es it ja pt_BR`) is initialised once, before it can be
  updated: `pybabel init -l <code> -i messages.pot -d translations`. After that
  one-time init, the locale rides the `update` step on every subsequent extract.

Commit, in one changeset, `messages.pot`, every `.po`, every `.mo`, **and** the
regenerated `services/js_i18n_strings.py` (step 0's output) — the §6 CI gate reds
if the manifest a developer commits differs from a fresh regeneration. There is
no build step on the user's machine (source-zip and PyInstaller bundle ship the
compiled catalogs as-is; `retrodb.spec` whitelists `translations/` in `DATAS`).

## 5. The pseudolocale

The pseudolocale is a permanent QA tool, not throwaway scaffolding. Each msgstr
is its msgid bracketed + accented (`Save` → `⟦Šàⱴé⟧`):

- **Bracketing** surfaces any *unwrapped* string — it renders plain English, no
  brackets, so a missed `_()` is visible at a glance.
- **Accenting + the bracket framing** widen each string, surfacing some
  layout/truncation bugs ASCII English hides. (The accent map is 1:1, so the only
  width delta is the `⟦⟧` brackets — there is no deliberate length-expansion pad.)
- **Placeholder guard.** Substitution tokens — gettext-named `%(name)s`, printf
  `%d`, and brace `{name}` — are passed through **un-accented and unbracketed**
  (`gen_pseudolocale.py::_PLACEHOLDER_RE`), so a `%(name)s` or `{n}` still
  interpolates at runtime. This is what lets the JS `t()` brace form (§6) survive
  the pseudolocale.

**Code:** `services.i18n.PSEUDO_LOCALE = 'eo'`. The natural CLDR pseudo-locale
`en_XA` is **not** parseable by the installed Babel (2.18.0;
`Locale.parse('en_XA')`
raises `UnknownLocaleError`), which would break date/number formatting and
display-name lookup. `eo` (Esperanto) is a real CLDR code Babel parses that the
project does not otherwise ship; the Settings dropdown
(`templates/_settings_tabs/library.html`, via `locale_display_name` in
`services/i18n.py`) always labels it the fixed string **"Pseudo"** (never its
`eo` endonym "Esperanto"). Everything that needs the code reads the constant —
never hard-code `'eo'`.

Select it in the UI via Settings → Display Preferences → Language, or send
`Accept-Language: eo`.

## 6. JS-side i18n (Pass 43.3)

Strings built in JavaScript (toast bodies, modal copy, confirm dialogs) cannot
ride the server `_()` path. They use a parallel **source-text** helper backed by
the same gettext catalog.

**The helper.** `t(msgid, params?)` lives in `static/js/utils.js` (the first
source concatenated into `core.bundle.js`). Its data, `window.I18N`, is set by the
**synchronous** nonce'd inline `<script>` in `base.html` (beside the existing
rating-system globals) — which runs *before* the `defer`-loaded `core.bundle.js`,
so both the helper and its map exist by the time any bundle code calls `t()`. Do
not move the `window.I18N` emission into a deferred/async script. It returns
`(window.I18N && window.I18N[msgid]) || msgid` — so an unbuilt/untranslated key
(or one whose translation is an empty string) degrades to the English source,
never to `undefined`. Optional `params` does
brace substitution: `t('Scraped {n} games', {n: 5})` replaces `{n}`. Brace
tokens are the only interpolation form (they survive the pseudolocale generator's
placeholder guard — see §5); do **not** concatenate translated fragments.

**`window.I18N`.** Emitted once in `base.html`'s existing nonce'd bootstrap
`<script>` (the page's root layout — child templates extend it, AJAX partials do
not, so the emission is once per full-page render), as
`window.I18N = {{ js_i18n_map()|tojson }};`. `js_i18n_map()` (a Jinja global in
app.py, registered beside `available_locales`) returns
`{msgid: _flask_gettext(msgid) for msgid in JS_I18N_KEYS}` for the active locale,
where `_flask_gettext` is `flask_babel.gettext` aliased at import
(`from flask_babel import gettext as _flask_gettext`) — the request-aware
translator, *not* stdlib `gettext` (same name, wrong behavior; alias it
explicitly). It carries **only** the
JS-used msgids, not the whole catalog, so the payload stays small.

**Performance.** `js_i18n_map()` and `field_labels_map()` (§7) are Jinja globals
called **once per full-page render** from `base.html`. Each loops `gettext` (an
in-memory lookup in the already-loaded catalog) over its key set — the few dozen
JS keys and the 81 canonical label values respectively — so the per-page cost is
a few hundred dict lookups: negligible, and not worth a cache. The one rule that matters: do **not** build
these in `inject_config` (the context processor at `app.py`, which fires ~30–50×
per page-navigation per its own Pass 34.2 cache comment) — that turns a once-per-
page loop into a per-partial / per-card one, the exact fixed cost Pass 34.2
removed. A `base.html`-scoped Jinja global keeps it once-per-page. (The adjacent
`window.RATING_IMAGE_MAP` etc. *do* ride `inject_config` — but those are
locale-*invariant* precomputed module constants, so passing a reference 30–50×
costs nothing. `js_i18n_map()` / `field_labels_map()` are locale-*aware* and
rebuild per call, so they must be Jinja globals, not `inject_config` values.
Emitting them in the same `<script>` block as the rating maps is fine; routing
them through the same context processor is not.)

**The msgid manifest + catalog bridge.** `services/js_i18n_strings.py` is an
**auto-generated** module (header marks it do-not-edit). `build_js.py`
regenerates it: it strips comments, regex-scans the non-bundle `static/js/*.js`
sources for `t('...')` / `t("...")` literal calls, **decodes** their JS escapes
(`…` → `…`, `\n`, `\'`, …) so a key matches what the JS engine actually
passes to `t()` at runtime, and writes the sorted unique set as **two** mirrors:

- `JS_I18N_KEYS` — the runtime list `app.py::js_i18n_map()` loops over to build
  `window.I18N`.
- `_EXTRACTION_ANCHORS` — the same msgids as literal `_('...')`
  (`lazy_gettext`) calls, so **`pybabel extract` pulls them into the catalog via
  the `[python:]` mapping**.

There is deliberately **no `[javascript:]` mapping** in `babel.cfg`: Babel's
JavaScript extractor mis-parses this codebase's template literals / ES6 and
silently drops `t()` calls (it extracted only ~40 of game-modals.js's strings).
`build_js.py`'s regex is the **single reliable reader**; the `_()` bridge routes
its output through Babel's solid Python extractor. The regex matches `t(` then a
single-/double-quoted string on one line (optional whitespace before the quote);
keep every `t()` argument a string literal.

**Non-literal `t()` calls** (`t(someVar)`) cannot be statically extracted; they
are a contract violation — a dynamic key silently falls back to English.

**CI / build gate.** `scripts/check_i18n_fresh.py` (run in CI) fails when:
(a) the **key set** parsed from a fresh regeneration of `services/js_i18n_strings.py`
differs from the committed module's `JS_I18N_KEYS` (a `t()` literal was added/
removed without rebuilding); (b) the **msgid set** of a fresh `pybabel extract`
differs from the committed `messages.pot`'s msgid set (a wrapped string was not
re-extracted); or (c) `JS_I18N_KEYS` is **not a subset** of the committed
`messages.pot` msgids. With the bridge, (c) holds by construction whenever the
module is fresh (the `_EXTRACTION_ANCHORS` mirror the keys), so a clause-(c)
failure means the committed module is stale relative to `messages.pot` — the same
class of bug as (a)/(b). All comparisons are over the parsed *set*, never raw file
bytes — the generator's formatting and the `.pot`'s `POT-Creation-Date` +
`#: file:line` location comments churn between runs and MUST be ignored, or the
gate red-lights unconditionally.

## 7. Canonical-label display translation (Pass 43.2)

The DB-stored canonical multi-value fields — `genre`, `perspective`,
`dimension`, `modes`, `game_structure` — keep **canonical English** at rest and
on the wire (filter values, API params, `data-filter-value`). Only the *rendered
label* is translated. The controller / query layer never sees a translated
token, so filtering and round-tripping are unaffected.

`region` is **excluded** — its values are user-configurable
(`region_options`), not a fixed canonical set.

**The layer.** `services/i18n_labels.py` holds:

- `I18N_LABEL_FIELDS = ('genre', 'perspective', 'dimension', 'modes',
  'game_structure')` — the single source of truth for *which* `FIELD_SCHEMAS`
  keys are translated. Both the anchor list (below) and the drift test read it,
  so they cannot drift apart. (`FIELD_SCHEMAS` also holds non-label keys —
  `save_type`, the eight `*_rating` keys, etc. — which this layer must not touch.)
- The canonical English value of each of those fields as literal `_('...')`
  anchors (`_` aliased to `flask_babel.lazy_gettext`), so `pybabel extract` pulls
  them into the catalog under the default keyword. **Lazy vs eager is
  deliberate:** the anchors must be `lazy_gettext` (evaluated at import, before any
  request context, purely to mark the msgid for extraction — they are never
  rendered), while `display_field_value` translates at render time with eager,
  request-aware `flask_babel.gettext`. Do not unify the two.
- `display_field_value(field, value)` — splits `value` on `,`, runs each token
  through eager `gettext`, rejoins with `', '`. `None`/`''` → `''`. A token with
  no catalog entry (a user-added dropdown value) passes through unchanged, since
  `gettext` returns its argument when there is no translation — the same
  fall-through the JS path gives (below). The `field` argument is accepted for
  call-site clarity and future `pgettext` context, but v1 uses one flat msgid
  namespace: it assumes the canonical values are **unique across all five
  fields** (verified — 81 values, zero cross-field collisions), so the field need
  not disambiguate the msgid. Registered as a Jinja global of the same name.

**Single home per token.** A canonical-field value (e.g. `'Single-Player'`,
`'Action'`) is translated **only** through this layer — never also wrapped with a
literal `_()` / `t()` elsewhere. Two homes means two msgids that can drift to
different translations for the same word.

**Server surfaces** (`templates/game_detail.html`): the genre filter-links and
the modes / perspective / dimension / game_structure text rows render
`display_field_value(...)`; the genre links keep their canonical
`data-filter-value`.

**JS surfaces.** `window.FIELD_LABELS` — `{ canonical: translated }` for every
`i18n_labels` value — is emitted in `base.html` alongside `window.I18N`, from a
`field_labels_map()` Jinja global (locale-aware, called once per page — see §6
Performance). A `tField(value)` helper (`utils.js`) splits on
`,`, maps each token via `window.FIELD_LABELS[token] ?? token`, and rejoins. It
is used wherever JS renders these fields as labels: the library/system card
genre (`all-games-controller.js`), the filter-modal option labels (the option
**value** stays canonical, only its visible text changes), the edit-modal tag
chips (`games.bundle.js`), and the game-detail modal genre/field rows
(`game-modals.js`, e.g. `gdmGenre`). User-added dropdown values absent from
`FIELD_LABELS` fall through to their English text — correct, since only the
built-in canonical set ships translations.

**Drift guard.** `tests/test_i18n_labels.py` asserts, iterating
`scraper/scrape_ai.py::FIELD_SCHEMAS` over the `I18N_LABEL_FIELDS` keys only:
(a) every value is covered by `i18n_labels` — so adding a canonical value without
a label entry fails CI — and (b) no value appears in two of those five fields, so
the flat-namespace assumption above can never silently break.

## 8. Tests

`tests/test_i18n.py` pins the full selector precedence — user-pref beats all,
session beats Accept-Language, Accept-Language when neither set, default `en`,
and stale-locale fallthrough — plus `available_locales()`, the locale validator
(accept/reject), the pseudolocale render + its coverage signal, and a
completeness scan asserting every visible string + user-visible attribute in the
rendered login pilot is bracketed under the pseudolocale. All locale assertions
read `PSEUDO_LOCALE`, so re-resolving the code updates the suite automatically.

`tests/test_i18n_labels.py` pins §7: `display_field_value` round-trips canonical
English unchanged under `'en'`, translates + preserves comma structure under the
pseudolocale, and both drift guards. The JS helpers (`t`, `tField`) have no
JS-side unit runner in this project; their *coverage* is guarded by the §6 CI
gate (every literal key is extracted and translated) rather than a runtime test,
and their behavior is exercised in the browser-walk verification step.

## 9. Long-form content — per-locale whole files (Pass 43.6)

Two surfaces are deliberately **not** translated through the gettext catalog: the
in-app **help manual** (`templates/help.html`, ~2000 lines) and the **changelog**
(`data/changelog.yaml`, ~800 release entries). Routing long-form prose with
inline markup through msgids makes the keys fragile (HTML bakes into the msgid)
and translates each document as disconnected fragments. Instead each is
translated as a **whole file per locale**, selected by the active locale with an
English fallback.

**Help manual.** `templates/help.<locale>.html` is a full translation of
`help.html`. The `/help` route (`app.py::help_page`) renders
`[f'help.{locale}.html', 'help.html']`, so Flask picks the localized file when it
exists and falls back to English otherwise. Invariants every `help.<locale>.html`
must hold (a structural recheck is cheap — compare the regex sets against
`help.html`):

- Every `id="..."` and `href="#..."` anchor is **byte-identical** to `help.html`
  — the in-page nav links break otherwise.
- Everything inside `<code>` / `<pre>` (commands, paths, config keys, URLs)
  stays English.
- Jinja constructs (`{% extends %}`, `{% block %}`, `{{ _('...') }}`,
  `{% trans %}`) are copied verbatim — the handful of catalog-backed strings
  still resolve through gettext.

Only visible prose, headings, nav-link text, and user-visible attributes are
translated. A locale with no file falls back to English; **partial coverage is
fine** (a missing locale is never an error).

**Changelog.** `data/changelog.<locale>.yaml` holds translated **recent** entries
only (the 3.8.x line onward as of 43.6). The `/changelog` route loads the full
English `changelog.yaml`, then **merges** any translated entry over the English
one **by version**, preserving the full timeline — older entries simply stay
English. Each translated entry **must repeat** `version`, `date`, and **every**
tag (each with its `type`) verbatim: the route swaps the whole entry in by
`version` (it does not merge field-by-field), so anything omitted from the locale
YAML — a field, or a tag present in the English entry — is dropped, not inherited.
Translate only each tag's `label` and the entry-level `body` (a sibling of
`tags`, not nested inside a tag), preserving all HTML tags/entities and product
names.

**Maintenance obligation (going forward).** When you add a changelog entry for a
release, also add its translated entry to each `data/changelog.<locale>.yaml`
(7 human-translation locales: `de fr es it ja pt_BR ko` — this is the long-form
translation set, distinct from the installed UI-catalog set that
`available_locales()` enumerates in §3) — otherwise that release renders English on
the changelog page for those users. When you materially change `help.html`
structure, mirror it into each `help.<locale>.html` (at minimum keep the `id` /
`href="#..."` anchors in sync). **Scoped out by design:** deep changelog history
(pre-3.8) stays English, and a locale may lag on help/changelog without breaking
anything — both fall back to English.
