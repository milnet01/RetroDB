### Accuracy (`assertions`)

**[CRITICAL] test_bulk_scrape_race.py:111 — Contradictory back-to-back assertions; line 111 always fails, making line 116 unreachable**

- **File:line:** `tests/test_bulk_scrape_race.py:111`
- **Evidence lines:** 111–116
- **Problem:** `assert job.job_id == first_id` at line 111 contradicts `assert job.job_id == queued_id` at line 116. After `swap_with_running` completes, `bulk_scrape.py:413` sets `self.job_id = new_running_job['job_id']` which is `queued_id`. `first_id` and `queued_id` are different values (separate job IDs generated by `_make_memory_db`). Line 111 will always raise `AssertionError`, so the test never passes and the actual intent (line 116) is never verified.
- **Consequence:** The regression test for the swap race condition never reaches its meaningful assertion. The fix it was written to guard (join-before-reset) is completely unverified. Any regression to the old `time.sleep` path would not be caught.
- **Fix:** Delete line 111 and its comment. The correct post-condition is `assert job.job_id == queued_id` (line 116 is right; line 111 is a leftover from confused author commentary).

### Flakiness (`flakiness`)

**[HIGH] test_graceful_shutdown.py:87 — Wall-clock timing assertion with a narrow upper bound**

- **File:line:** `tests/test_graceful_shutdown.py:87`
- **Problem:** `assert elapsed < 1.5` on a test that calls `request_shutdown(timeout=2.0)` and waits for a thread. The 2.0 s timeout is larger than the 1.5 s guard. On a heavily loaded CI runner, the thread join could legitimately consume 1.5–2.0 s even when the implementation is correct.
- **Consequence:** Sporadic CI failure on loaded machines: the test would fail even though the implementation is working as intended — the cancel event is set, the thread exits, but scheduling jitter pushed elapsed past 1.5 s.
- **Fix:** Either tighten the `request_shutdown(timeout=...)` call to 0.5 s (the fast path should complete well under that) so the 1.5 s bound is clearly safe, or raise the assertion bound to `< timeout * 1.5` so it scales with the chosen timeout.

**[MED] test_graceful_shutdown.py:104 — Lower-bound timing assertion is flaky under scheduler jitter**

- **File:line:** `tests/test_graceful_shutdown.py:104`
- **Problem:** `assert 0.2 < elapsed` with `timeout=0.3`. Under a lightly loaded or high-resolution machine, the join can return in under 0.2 s on some platforms even with a 0.3 s timeout (join precision is OS-scheduler-dependent).
- **Consequence:** Occasional false failure on fast/low-contention CI. The meaningful assertion is the upper bound (`< 1.0`); the lower bound adds brittleness without safety value.
- **Fix:** Remove the lower bound `0.2 <` or lower it to `0.05 <`. The intent (proves shutdown doesn't return instantly when thread is stuck) is better served by checking `stuck._thread.is_alive()` after the call than by a timing floor.

**[MED] test_bulk_scrape_race.py:132 — `time.sleep(0.05)` in worker stub is a busy-poll alternative that may slow the test suite on loaded CI**

- **File:line:** `tests/test_bulk_scrape_race.py:132`
- **Problem:** The `slow_worker` in `TestDemoteWaitsForWorkerExit` loops with `time.sleep(0.05)` while waiting for a cancel flag. In `TestSwapWaitsForWorkerExit` (lines 79–80) the same stub uses `worker_can_exit.wait(timeout=0.05)` — a proper blocking wait. The demote test's pattern is inconsistent: it will busy-loop sleeping until cancel is set. The loop bounds depend on how quickly `demote_running()` sets the cancel flag, and on CI could run many iterations before the flag is observed (each iteration burns real wall time and a context switch).
- **Consequence:** Not a correctness flake, but the demote test consistently consumes more wall time than the swap test for the same scenario; under parallel test execution the sleeping thread holds a real OS thread for the full spin.
- **Fix:** Replace `time.sleep(0.05)` with `threading.Event.wait(timeout=0.05)` on a shared event (mirror the swap test's pattern), or simply check `self.cancelled` without sleep since the cancel flag check is the only branch.

### Isolation (`isolation`)

**[HIGH] test_emulator_registry_routes.py:16 — `open('routes/emulators.py')` uses a CWD-relative path**

- **File:line:** `tests/test_emulator_registry_routes.py:16`
- **Problem:** `src = open('routes/emulators.py').read()` depends on the working directory being the project root at test runtime. If pytest is invoked from a different directory (e.g. `pytest tests/test_emulator_registry_routes.py` from `/home/user`), the open will raise `FileNotFoundError` and the test fails for an environmental reason unrelated to the code under test.
- **Consequence:** Test breaks silently when run outside the repo root — common in CI containers where the working directory varies.
- **Fix:** Use `pathlib.Path(__file__).resolve().parent.parent / 'routes' / 'emulators.py'` (mirrors the `_REPO_ROOT` pattern already used in `test_emulator_seeder.py:8`).

**[MED] test_database_backup.py:136 — Monkey-patches `db_mod.sqlite3.connect` directly on the module attribute without using `monkeypatch`**

- **File:line:** `tests/test_database_backup.py:136`
- **Problem:** `db_mod.sqlite3.connect = fake_connect` modifies a module-level attribute without pytest's `monkeypatch` fixture. The `finally` block (line 143) restores it, but any exception *before* `fake_connect` is assigned (e.g. in `_populate`) would skip the finally in a way that leaves the global patched — though in practice the structure is safe. More critically: if a future edit adds a test in the same session that concurrently uses `db_mod.sqlite3.connect`, the patch bleeds.
- **Consequence:** Not a current bug given the try/finally, but the pattern is fragile; `monkeypatch.setattr(db_mod.sqlite3, 'connect', fake_connect)` would make restoration automatic and thread-safe.
- **Fix:** Accept `monkeypatch` as a parameter and use `monkeypatch.setattr(db_mod.sqlite3, 'connect', fake_connect)` — eliminates the manual restore.

**[MED] test_graceful_shutdown.py:60–63 — `shutdown_requested` event modified without fixture teardown guard in `test_sets_shutdown_event`**

- **File:line:** `tests/test_graceful_shutdown.py:60`
- **Problem:** `test_sets_shutdown_event` calls `base_mod.shutdown_requested.clear()` before and after the assertion, but there is no `try/finally`. If the assertion fails (line 62), the second `.clear()` on line 63 is never reached, and `shutdown_requested` is left set for subsequent tests in the same session.
- **Consequence:** If `test_sets_shutdown_event` fails, all tests that run after it within the same process and check `shutdown_requested` will see a stale set state, producing cascading failures.
- **Fix:** Wrap lines 61–63 in a `try/finally`: `base_mod.shutdown_requested.clear()` in the finally block. Or use a fixture that clears the event before and after each test.

### Determinism (`determinism`)

**[MED] test_emulator_seeder.py:76–78 — Hardcoded count `n_emu == 12` will break when `emulator_seeds.json` grows**

- **File:line:** `tests/test_emulator_seeder.py:76`
- **Problem:** `assert n_emu == 12` hardcodes the exact count of emulators in `data/emulator_seeds.json`. The seed file currently has exactly 12 emulators, so this passes. But the test is asserting idempotency — "running seed twice doesn't double-insert" — not "there are exactly 12 emulators". When a new emulator is added to the seed file, this test will fail for the wrong reason.
- **Consequence:** Every new emulator addition requires a test edit; the test will block the feature, causing developer confusion about whether the seed or the test is wrong.
- **Fix:** Replace `assert n_emu == 12` with `assert n_emu >= 12` or, better, seed once and record the count, then seed again and assert the count is unchanged: `count_before = ...; seed(); count_after = ...; assert count_after == count_before`.

### Verbosity / Parametrisation (`verbosity`, `parametrisation`)

**[LOW] test_formatters.py:38–56 — Manufacturer lookup tests are individually named instead of parametrized**

- **File:line:** `tests/test_formatters.py:38`
- **Evidence lines:** 38–56 (`test_nintendo_consoles`, `test_sony_consoles`, `test_sega_consoles`, `test_microsoft_consoles`)
- **Problem:** Four test methods, each asserting 2–4 manufacturer lookups, but grouped by brand. This is a natural parametrize candidate: `(folder, expected_manufacturer)` tuples.
- **Consequence:** Adding a new manufacturer requires adding a whole new method; failure message only says which brand-group failed, not which specific folder.
- **Fix:** `@pytest.mark.parametrize("folder, expected", [('nes','Nintendo'), ('psx','Sony'), ...])` as a single test function.

**[LOW] test_game_utils.py:21–50 — Article movement tests each assert one input/output pair**

- **File:line:** `tests/test_game_utils.py:21`
- **Evidence lines:** 21–50 (9 methods for `TestArticleMovement`)
- **Problem:** `test_leading_the_moves_to_end`, `test_leading_a_moves_to_end`, `test_leading_an_moves_to_end`, etc. each assert a single `(input, expected_output)` pair. Parametrize would halve the line count and add new cases with one tuple.
- **Consequence:** Low — the tests are clear and functional. Pure verbosity: 9 methods → 1 parametrized test.
- **Fix:** `@pytest.mark.parametrize("title, expected", [...])` for the `move_article_to_end` cases; same for `move_article_to_beginning`.

**[LOW] test_emulator_seeder.py:28–64 — Three consecutive tests each repeat the `seed_emulators_from_file(db, ...)` call at the top**

- **File:line:** `tests/test_emulator_seeder.py:29`
- **Problem:** `test_seeder_inserts_emulators`, `test_seeder_inserts_system_emulators`, and `test_seeder_skips_unknown_system_folders` all start with an identical `from services.emulator_seeder import seed_emulators_from_file; seed_emulators_from_file(db, ...)` call. Each test seeds then queries a different result.
- **Consequence:** If the seeder import path changes, three tests need editing. The repeated seed call is setup, not the assertion — it belongs in a fixture or autouse.
- **Fix:** Either use an `autouse=True` fixture that runs the seed once per test, or run the seed at fixture level (a second fixture that wraps `db` and calls the seeder).

### Coverage Gaps (`coverage_gaps`)

**[MED] test_database_backup.py — No test for the case where the destination directory does not exist**

- **File:line:** `tests/test_database_backup.py:24` (nearest anchor)
- **Problem:** `backup_database(src, dst)` receives a `dst` path whose directory is guaranteed to exist (inside `tempfile.TemporaryDirectory`). The helper's behaviour when the destination directory is missing (e.g. `backup_database(src, '/nonexistent/dir/dst.db')`) is untested.
- **Consequence:** If `backup_database` silently passes a non-existent directory to `sqlite3.connect` (which SQLite auto-creates), the error path is untested. If it raises before connect, that's also untested.
- **Fix:** Add `test_backup_missing_destination_dir` — call with `dst = os.path.join(tmp, 'subdir', 'dst.db')` (subdir never created) and assert either it raises a known exception type or it succeeds (documenting the contract).

**[MED] test_emulator_registry_routes.py — No test for DELETE handler**

- **File:line:** `tests/test_emulator_registry_routes.py:30` (nearest anchor: `TestEmulatorCRUD`)
- **Problem:** `TestEmulatorCRUD` has `test_admin_can_list`, `test_admin_can_create`, `test_admin_can_update`, and `test_viewer_cannot_create`. There is no test that verifies the DELETE route (`DELETE /api/emulators/<id>`) is present and admin-only.
- **Consequence:** The authorization guard on DELETE is asserted structurally in `test_mutating_routes_require_admin` (line 15) only by regex-scanning the source, not by exercising the route. A bug that accidentally strips the decorator from the delete handler would not be caught behaviourally.
- **Fix:** Add `test_admin_can_delete` and `test_viewer_cannot_delete` following the existing CRUD pattern.
