### FLAKINESS

**[HIGH] test_launcher_local.py:40–47 — Poll loop with `time.sleep(0.05)` has no assertion message on timeout**  
Tests `test_launch_quick_exit_reaps_cleanly` (line 46), `test_launch_failed_exit_code_propagates` (line 66), and `test_kill_idempotent_on_already_exited` (line 101) all spin `while time.time() < deadline: time.sleep(0.05)`. On a slow CI runner where `/bin/true` or `/bin/false` reap slowly (e.g. under memory pressure), the loop exits with `st` still `None` or in `'running'` state and the following `assert` fires with no diagnostic about *which* state was seen.  
The pattern is safe functionally (deadline=2s, `true`/`false` exit in <1ms normally), but CI under saturation has produced failures here. The real risk is the `sleep(0.05)` hard minimum latency: 3 tests × 0–2s each = up to 6s of potential wait time per run.  
**Fix:** Replace the manual poll with a utility: `_poll_exited(launcher, token, deadline_s=2.0)` extracted to a local helper; use `pytest.fail(f"timed out waiting for state; last={st!r}")` on deadline breach rather than relying on the downstream assertion.

**[HIGH] test_migrations.py:210 — `time.sleep(0.01)` to ensure `updated_at` advances**  
`test_update_refreshes_updated_at` inserts a row, sleeps 10 ms, updates it, then asserts `second[0] > first[1]` (string comparison of ISO timestamps). SQLite's `strftime('%Y-%m-%dT%H:%M:%fZ', 'now')` has millisecond precision, so 10 ms *should* be sufficient — but under scheduler jitter or OS timer coarseness (Windows, some hypervisors) the two strftime calls may return the same value, producing a spurious failure.  
**Fix:** Either freeze time via monkeypatching the trigger's `'now'` (not straightforward in SQLite), or update the row twice with a forced different `updated_at` value in the first insert (`conn.execute("UPDATE games SET updated_at = '2000-01-01T00:00:00.000Z' WHERE id=?", (id,))`), then verify the trigger overwrites it with a later value — no sleep needed.

**[MED] test_observability.py:108–117 — Subprocess test uses `cwd='.'`**  
`test_factory_returns_dash_with_no_request_context` spawns a subprocess with `cwd='.'`. This resolves to the process's current working directory at pytest invocation time. If pytest is run from a directory other than the project root (e.g. `pytest tests/` from a subdirectory, or IDE runners that set cwd to `tests/`), `import log_manager` inside the subprocess fails with `ModuleNotFoundError`, making the test fail for environmental rather than behavioural reasons.  
**Fix:** `cwd=str(Path(__file__).resolve().parent.parent)` to anchor to the project root.

### ISOLATION

**[HIGH] test_log_redactor.py:94–105 — `install_global_redactor()` mutates root logger filters with no teardown**  
`test_root_filter_is_idempotent` calls `log_manager.install_global_redactor()` twice, which adds a `SecretRedactor` to `logging.getLogger().filters`. The test manually strips pre-existing `SecretRedactor` instances at the start (line 99) but does not strip the one it adds at the end. Any test in *any file* that subsequently checks `logging.getLogger().filters` or is sensitive to log output being redacted inherits this mutation.  
`test_install_covers_basicconfig_handler` (line 107) adds a `StreamHandler` to the root logger inside `try/finally` and removes it — that part is correct. But it also calls `install_global_redactor()` again, which (because the global `_request_id_installed` / `_redactor_installed` flag is set) is a no-op only if idempotency is implemented — worth verifying.  
**Fix:** Add `root.filters = [f for f in root.filters if not isinstance(f, SecretRedactor)]` to a `finally` block (or a fixture with `yield`) so the filter is always removed after each test.

**[MED] test_observability.py:13 — Module-scoped `client` fixture installs `install_request_id_factory()` globally**  
The module-scoped `client` fixture imports `app`, which at import time calls `install_request_id_factory()`, setting `log_manager._request_id_installed = True` and replacing `logging.getLogRecordFactory()` globally. This mutated factory persists for the entire pytest session, affecting any test file that subsequently creates `LogRecord`s and does not expect the `request_id` attribute. There is no teardown.  
This is partially mitigated (the factory is additive — it sets `record.request_id` which most tests don't check), but `TestRequestIdFactory.test_record_has_request_id_attribute` (line 73) calls `install_request_id_factory()` again — which is silently a no-op because `_request_id_installed` is already `True`. The test still passes because the factory was installed by the module fixture, not by the explicit call. The test is testing the wrong thing: it appears to verify that its own `install_request_id_factory()` call works, but the behaviour is actually already in effect from fixture side-effects.  
**Fix:** Use `monkeypatch` to reset `log_manager._request_id_installed = False` and `logging.setLogRecordFactory(original_factory)` in a teardown so each test exercises a clean state.

**[MED] test_migrations.py:293–298 — `migrations.MIGRATIONS` mutated without `monkeypatch`**  
`TestCollectionsOwnerId.test_backfill_assigns_legacy_rows_to_admin` directly assigns `migrations.MIGRATIONS = real_list[:1]` inside a `try/finally`, which correctly restores it. However the direct mutation (rather than `monkeypatch.setattr`) means if the test is killed mid-run (SIGKILL, OOM), the global list is never restored, leaving subsequent tests in the same session operating on the truncated list.  
By contrast, `test_failed_migration_rolls_back_and_keeps_version` (line 108) uses `monkeypatch.setattr` correctly for the same global.  
**Fix:** Replace the `try/finally` manual mutation with `monkeypatch.setattr(migrations, 'MIGRATIONS', real_list[:1])` — monkeypatch guarantees cleanup even under exception/SIGTERM.

### DETERMINISM

**[MED] test_migrations.py:209–215 — Timestamp comparison is order-dependent on string sort**  
`assert second[0] > first[1]` compares two ISO-8601 strings (e.g. `"2025-05-17T10:22:33.123Z"`). String lexicographic order matches chronological order for this format, so this is correct — but only if both timestamps are formatted identically (same precision, same suffix). If the trigger format ever changes (e.g. drops the `Z`, changes to local time, or uses a different precision) the comparison silently becomes wrong. A datetime parse would make the intent explicit and be robust to format changes.  
**Fix:** `assert datetime.fromisoformat(second[0].rstrip('Z')) > datetime.fromisoformat(first[1].rstrip('Z'))` to make the ordering semantics clear.

**[LOW] test_launcher_registry.py:64–66 — `started_at=time.time() - 3.0` uses wall clock**  
`test_gc_removes_exited_after_ttl` seeds a registry entry with `started_at=time.time() - 3.0` and marks it exited at `exit_time=time.time() - 2.0`. The TTL logic (`post_exit_ttl_s=1.0`) computes `now - exit_time > 1.0`. This works but relies on `time.time()` not moving during test setup. Under extremely heavy load or virtualised time sources, if the clock moves backward or stalls between the two `time.time()` calls, the condition may not hold.  
**Fix:** Use a fixed baseline: `t = time.time(); registry.register(..., started_at=t - 3.0); registry._mark_exited('gone', exit_time=t - 2.0)` — single `time.time()` call, offsets stay consistent.

### ASSERTIONS

**[MED] test_museum_job.py:81 — `worker_finished.wait(timeout=2.0)` return value asserted without message**  
`assert worker_finished.wait(timeout=2.0)` — when the event is not set within 2 seconds, the assertion fires as `AssertionError` with no diagnostic. In CI this shows up as a bare failure with no information about whether the worker thread raised an exception, what state the job is in, or whether the timeout was too tight.  
**Fix:** `assert worker_finished.wait(timeout=2.0), f"Worker thread did not finish within 2s; job state: {job.get_status()!r}"`

**[MED] test_launcher_local.py:47 — Compound assertion hides individual failures**  
`assert st is not None and st.state == 'exited'` — if `st is None`, the right side is short-circuited and the failure message is `AssertionError` with no information about the final state. Same at line 67.  
**Fix:** Split: `assert st is not None, "poll loop never set st"` then `assert st.state == 'exited'`.

**[LOW] test_migration_012.py:78 — Hardcoded index position 11 is fragile**  
`assert MIGRATIONS.index('012_emulators') == 11` — this is the correct value today (verified: list has 12 items, 0-indexed position 11). But any future migration inserted between 001–011 will shift this and make the test fail with a confusing error. The test is trying to prove that the migration is in the right *slot*, but the real invariant is that it's in the list and applied in the right *order relative to its predecessor*.  
**Fix:** `assert MIGRATIONS[11] == '012_emulators'` is slightly better framing, but the more robust form is: `assert MIGRATIONS.index('012_emulators') == MIGRATIONS.index('011_user_game_views_cascade_fk') + 1`.

### VERBOSITY / PARAMETRISATION

**[MED] test_metadata_merger.py — `_blank_metadata()` + `_blank_result()` called 30+ times inline**  
Every single test method in the file calls both `_blank_metadata()` and `_blank_result()` as its first two lines. This is 60+ near-identical setup lines. The helpers are file-local functions, not fixtures, so they aren't composable with pytest fixture scope.  
**Fix:** Convert both to a `@pytest.fixture` pair (or a single combined fixture returning a `(meta, result)` tuple), or use an autouse fixture at the class level. The payoff is smaller tests and uniform setup.

**[LOW] test_metadata_merger.py:53–112 — Fill-only contract tested per-source but the invariant is the same**  
`TestApplyTgdb` has `test_fill_only_true_preserves_existing_non_title_fields`, `test_fill_only_false_overwrites_title`, `test_fill_only_true_keeps_existing_title`. `TestApplyRawg` has near-identical versions. The fill-only contract is a shared concern but tested in a divergent, copy-varied way.  
**Fix:** A cross-source parametrize block (`@pytest.mark.parametrize("apply_fn,source_data,field", [...])`) would pin the same invariant once. Within-class duplication is acceptable but the naming divergence (`preserves_existing_non_title` vs `keeps_existing`) obscures that they're the same contract.

### COVERAGE GAPS

**[MED] test_log_redactor.py — No test for `kwargs`-style log record args (dict interpolation)**  
`TestSecretRedactorFilter` tests positional tuple args (`args=(jwt,)`) but not dict-style args (`args={'token': jwt}`, used when a logger is called as `logger.info("got %(token)s", {'token': jwt})`). If `SecretRedactor.filter` only iterates over `args` as a sequence and receives a dict, it may skip redaction. This is a gap adjacent to the tested path.  
**Fix:** Add `test_filter_redacts_dict_args` with `args={'val': jwt}` and confirm the JWT is redacted.

**[MED] test_museum_job.py — No test for `resume_from_params` when `progress=None`**  
`TestResumeFromParams.test_resume_skips_already_processed_indices` passes `progress={'current': 3, ...}`. The case where `progress=None` (first-time start with no prior progress) is only exercised indirectly. A dedicated test for `progress=None` → `resume_index == 0` would document the expected behaviour explicitly.

**[LOW] test_launcher_factory.py — No test for the default when `launcher_backend` setting is absent (returns `None`)**  
`test_factory_returns_local_when_setting_local` patches `get_setting` to return `'local'`. `test_factory_raises_for_unknown` uses `'spaceship'`. But `get_setting` returning `None` (setting absent, using `default=None`) is the "unconfigured" path — it's unclear if the factory treats `None` as `'local'` (safe default) or raises. This path has no coverage.

### PERFORMANCE / FIXTURE SCOPE

**[LOW] test_observability.py:13 — Module-scoped `client` shares state across `TestSlowRequestLogging` tests that use `caplog`**  
The `client` fixture is module-scoped, which means a single Flask test client is reused across all four test classes. `TestSlowRequestLogging.test_fast_request_does_not_log` and `test_probe_endpoints_exempt_from_slow_log` both use `caplog`, which captures records from the entire logging hierarchy. Because the module-scoped client may have left background log records from earlier tests in the same module, `caplog` records are not guaranteed clean at the start of these tests. Currently the tests filter on `'slow_request'` in the message, which mitigates this — but it's fragile to future log message changes.  
**Fix:** This is low severity given the message filter, but consider making the `client` fixture function-scoped or adding a `caplog.clear()` call at the start of each slow-log test.
