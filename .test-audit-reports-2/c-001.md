## Findings

### Dimension 5 — Flakiness Risk

**MED** · `tests/test_bulk_scrape_race.py:102,106,150,152` — Thread synchronisation timeouts (2.0 s, 5.0 s) are hard-coded literals with no diagnostic on breach. On a heavily loaded CI runner the 2-second `worker_observed_cancel.wait(timeout=2.0)` could legitimately time out (the worker loop polls every 50 ms; under scheduling pressure that can accumulate). The assertion failure message is the pytest default (`AssertionError`), with no context about which event timed out or what state the job was in.
- **Consequence:** Intermittent CI failures on oversubscribed runners with no actionable log.
- **Fix:** Capture the wait result: `observed = worker_observed_cancel.wait(timeout=2.0); assert observed, f"Worker never observed cancel — job.cancelled={job.cancelled!r}, job.running={job.running!r}"`. The timeout itself is adequate; the message is not.

### Dimension 6 — Test Isolation

**MED** · `tests/test_auth_hardening.py:53` — `app_module.app.config['TESTING'] = True` assigned directly with no teardown inside `test_login_endpoint_rejects_missing_user_id`. If this test runs before any other test that expects `TESTING` to be `False` (or unset), those tests see the mutated config. No `monkeypatch.setitem` wrapper.
- **Consequence:** Under `pytest-xdist` or any test-ordering variation, tests that branch on `app.config['TESTING']` may behave differently depending on whether this test ran first.
- **Fix:** `monkeypatch.setitem(app_module.app.config, 'TESTING', True)` — pytest resets it on teardown automatically. Same pattern already used correctly for `_db_pool` in `_isolated_db()` (line 274).

**MED** · `tests/test_auth_hardening.py:134` — Same bare `app_module.app.config['TESTING'] = True` mutation in `test_login_endpoint_reachable_and_clears_session`, same no-teardown pattern.
- **Fix:** Same as above.

**MED** · `tests/test_auth_hardening.py:373` — Class-scoped fixture `client` sets `app_module.app.config['TESTING'] = True` with no teardown. Class-scoped fixtures run once per class and their teardown only fires at class teardown — but `app.config` is a module-level singleton. If a later test class in the same process doesn't set `TESTING=True`, it will run with whatever value this fixture left behind.
- **Consequence:** Three separate tests (`test_login_endpoint_rejects_missing_user_id`, `test_login_endpoint_reachable_and_clears_session`, and the `TestDestructiveEndpointsRequireAuth` fixture) all mutate the same dict key without coordinated teardown. The accumulated state is always `True`, which is probably harmless in practice, but is a latent ordering bug if any future test asserts `TESTING is False`.
- **Fix:** `monkeypatch.setitem(app_module.app.config, 'TESTING', True)` — requires promoting the fixture to function scope or accepting a `monkeypatch` parameter.

**LOW** · `tests/test_assets.py:26–27` — `assets._MANIFEST_CACHE['mtime'] = 0` and `assets._MANIFEST_CACHE['data'] = {}` are direct mutations of a module-level dict inside the `app_with_manifest` fixture, done without `monkeypatch`. The fixture is function-scoped (default), so each test entry does reset the cache — but there is no corresponding teardown that restores the cache after the fixture yields. If a test modifies `_MANIFEST_CACHE` during its run (as `test_manifest_cache_refreshes_on_mtime_change` does implicitly via `asset_url()`), the post-yield state is whatever the test left behind. Under `pytest-xdist` this is a data race between workers.
- **Consequence:** Unlikely to fail in serial test runs because every entry resets the dict. Under parallel execution, two workers sharing the same Python process could interleave cache reads/writes.
- **Fix:** `monkeypatch.setitem(assets._MANIFEST_CACHE, 'mtime', 0)` and `monkeypatch.setitem(assets._MANIFEST_CACHE, 'data', {})` inside the fixture — requires adding `monkeypatch` to the fixture's parameter list.

### Dimension 3 — Coverage Gaps

**LOW** · `tests/test_bulk_scrape_race.py:120–154` — `TestDemoteJobOrdering.test_demoted_job_state_only_resets_after_worker_exits` asserts that `demote_done` fires within 5 seconds (the join doesn't time out) but makes no assertion about the job's state after the demote completes. The test verifies timing safety but not correctness of the state transition: it does not check that `job.job_id` changed to the queued job's ID, that the old job was re-queued, or that counters were reset. Compare with `TestSwapJobOrdering` which explicitly checks `job.job_id == queued_id` and `job._queue[0]['job_id'] == first_id`.
- **Consequence:** A regression in `demote_running()` that fixes the timing (join present) but scrambles the resulting state would pass this test.
- **Fix:** After `assert demote_done.wait(timeout=5.0)`, add: `assert job.running is True` (new head is now running), `assert len(job._queue) == 1` (old running job demoted to queue), and optionally `assert job.job_id != first_id`.

**LOW** · `tests/test_backup_rotation.py` — No test for the case where the backup directory does not exist. `_prune_old_backups` is called with a `tmp` dir that always exists. If the function is called with a non-existent path, behaviour is uncovered (raises `FileNotFoundError`, or silently no-ops?).
- **Fix:** Add `test_nonexistent_directory_is_noop_or_raises` that calls `_prune_old_backups('/nonexistent/path/xxx', keep=3)` and asserts either no raise or specific exception.

### Dimension 15 — Performance

**LOW** · `tests/test_auth_hashing.py` — The prior HIGH finding ("4 × `hash_password()` calls at production PBKDF2 iteration count") was the top performance item in the prior synthesis. **This is now fully fixed.** `TEST_ITERATIONS = 1` (line 23) is used everywhere except `test_pbkdf2_iterations_meets_owasp_floor` (line 40–44), which reads `PBKDF2_ITERATIONS` without hashing. The `_make_legacy_hash()` helper uses `100_000` iterations — this is used by two tests (`test_verify_accepts_legacy_format` and `test_needs_rehash_flags_legacy_format`). At 100k PBKDF2-SHA256 iterations, each call takes approximately 30–80 ms on modern hardware (vs ~1.5 s at 600k). Two calls = ~60–160 ms total, which is acceptable. This is a confirmed fix — no remaining action needed.
